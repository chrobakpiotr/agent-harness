# AH5-13 — contract-validation findings kept verbatim (register, 2026-10-20)

Recorded at master's order. AH5-13 moved these rules unchanged; none is fixed silently, in AH5-13 or in AH5-14a. Line
numbers are Showcase `fd96eeb`; library `agent_harness.verification_contract` as released in 0.15.0.

**Where the validator gates work.** Showcase's `harness.validate()` (`harness.py:455`) adds `validate_contract`'s
errors, and `load_validated()` (`harness.py:3631`) refuses an invalid feature. About 45 call sites go through it,
including `cmd_start` (`harness.py:6826`) and the complete path (`harness.py:5396`, `:5518`). `wayfinder.py:887`
requires a valid contract before `to-tasks`. `criterion_ids` feeds the accepted criteria that task acceptance criteria
and evaluator coverage are checked against (`harness.py:604`, `:650`, `:4326`).

| # | Finding | Trigger | Current behaviour | Possible effect | Proposed change | Severity |
|---|---|---|---|---|---|---|
| F1 | **Fail-open staleness** | Any input cannot be hashed while `verification-contract.json` exists: `repo_root()` dies (no Git, or neither the harness checkout nor the working directory is in a repository), or a hashed file raises `OSError` (the constitution moved or deleted, an unreadable `spec.md`/`plan.md`/design record). | `validate_contract` catches `OSError`/`SystemExit` from `input_hashes` and skips the **whole** staleness check (`expected = {}`); the other rules still run. | A contract written for an older spec, plan, constitution or design record validates. `load_validated` then lets `start` and `complete` proceed, so work can be **executed and accepted against stale criteria**. | Fail closed: if any input cannot be hashed, add an error such as `verification contract staleness cannot be established: <input>`; never treat an unreadable input as matching. A behaviour change for Showcase: a feature that validates today in such a state would be refused. | **medium — reported before the admission migration (AH5-14c)** |
| F2 | Exemption `scope`/`reason` not checked | An exemption with `status: accepted`, `approved_by: human…`, but no `scope` or `reason`. | Accepted. The schema (`schemas/verification-contract.schema.json`, describing the author's result) requires `id`, `scope`, `reason`, `status`, `approved_by`. | An approved exemption with no stated scope. Today nothing in Showcase's harness consumes exemptions (no reader besides the validator), so no execution or acceptance depends on it; an audit record is incomplete. | Require non-empty `scope` and `reason` for every exemption. | low |
| F3 | Criterion id pattern looser than the schema | A criterion id such as `VC-x` or `VC-0001`. | Accepted (`startswith('VC-')`); the schema says `^VC-[0-9]{3}$`. | Such ids enter `criterion_ids`, so tasks may reference them and evaluators must cover them. No criterion is dropped; ids are only less uniform. | Check `^VC-[0-9]{3}$` (and decide whether existing contracts need a migration). | low |
| F4 | Anonymous human approval | `approved_by: "human:"`. | Accepted (`startswith('human:')`); the doc says `human:<name>`. | An exemption marked as approved by a human without naming one. Not consumed downstream today (F2). | Require a non-empty name after `human:`. | low |
| F5 | Latent crashes on malformed contracts | `inputs` that is not an object; `criterion_ids` on a contract that is not an object. | `AttributeError` propagates. | Fails closed (the caller crashes instead of accepting); poor diagnostics only. | Report a validation error instead of raising. | low |

Not divergences: whitespace-only `statement`/`sources` are refused, stricter than the schema's `minLength 1`;
`schema_version == 1`, `status == 'accepted'`, the feature-name match and the `optional` default are not specified by
the doc and are kept as the source has them.

Each fix is a behaviour change to agreed rules and needs its own decision (owner/master), a packet with old/new
behaviour, consumer impact and tests. F1 should be decided before AH5-14c moves admission.
